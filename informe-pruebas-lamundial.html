Pruebas sobre la API de Emisión RCV

La Mundial de Seguros  ·  Entorno QA  ·  20 de abril de 2026

En el marco del desarrollo de una plataforma intermediaria para la emisión automática de pólizas RCV en viajes de taxi por aplicación, realizamos pruebas de integración contra el entorno QA de la API documentada en «Documentación Uso de Endpoints – Emisión RCV V2.1».

El objetivo fue validar el flujo completo de 8 pasos hasta la emisión de una póliza de prueba, usando un vehículo tipo taxi (Chevrolet Aveo 2018, categoría 6 – Alquiler con chofer / Taxi). A continuación se detallan los resultados obtenidos, las inconsistencias encontradas en la documentación y los requerimientos pendientes para continuar la integración.

Inconsistencias encontradas en la documentación V2.1

Los siguientes problemas fueron identificados durante las pruebas. Se solicita revisión y corrección.

#InconsistenciaDescripciónAcción requerida
1 /inma/year — método HTTP incorrecto El documento indica GET, pero el servidor solo responde a POST. Confirmado en prueba. Corregir a POST en la documentación oficial.
2 Campo año vs fano La tabla de campos (pág. 9) llama al año del vehículo año. El JSON de ejemplo (pág. 10) usa fano. La API responde a fano. Confirmar el nombre oficial del campo en producción y unificar la documentación.
3 Typo: estado_civi_tomador La tabla de campos (pág. 8) usa estado_civi_tomador (sin la l final). El JSON de ejemplo usa estado_civil_tomador. Confirmar el nombre exacto del campo para tomador y titular.
4 Respuesta de getCotizacionAuto incorrecta El documento (pág. 7) muestra como respuesta una lista de categorias_uso. La respuesta real contiene mprima, mprimaext y ptasa. Es un error de copy-paste del endpoint anterior. Actualizar el ejemplo de respuesta en la documentación.
5 Entorno DEV caído https://devapisys2000.lamundialdeseguros.com no responde (error de conexión / SSL). Solo el entorno QA está operativo. Reportar al equipo de infraestructura.
6 Autenticación completamente ausente El endpoint createEmissionAuto exige un Bearer Token que no aparece en el documento. No hay endpoint de login, credenciales de prueba ni descripción del flujo de autenticación. Proveer documentación del flujo de autenticación.

Requerimientos pendientes — solicitud formal

Los siguientes elementos son necesarios para continuar el desarrollo e ir a producción. Se solicita formalmente su provisión por parte de La Mundial de Seguros.

RequerimientoDetallePrioridad
Credenciales de autenticación QA Usuario y contraseña (o API Key) para obtener el Bearer Token en el entorno QA. Sin esto no es posible probar la emisión. Crítico
Endpoint de login / token URL y método del endpoint que devuelve el Bearer Token. ¿Expira? ¿Cuánto dura? ¿Cómo se refresca? Crítico
Código de productor asignado El ejemplo del documento usa 80080. Cada cliente debe tener un código propio. Necesitamos el nuestro para QA y Producción. Crítico
Endpoint de cancelación de póliza El sistema emite una póliza al inicio de cada viaje y debe cancelarla al finalizar. No existe ningún endpoint de cancelación en la documentación V2.1. ¿Existe? ¿Cómo funciona? Crítico
Confirmación: campo año o fano Confirmar el nombre definitivo del campo año del vehículo en el body de createEmissionAuto y en producción. Importante
Confirmación: estado_civil_tomador Confirmar el nombre exacto del campo de estado civil del tomador y titular para evitar rechazos en emisión. Importante
Documentación del entorno Producción Proceso para migrar de QA a Producción, credenciales, diferencias de configuración y SLA del servicio. Planificación

Próximos pasos
