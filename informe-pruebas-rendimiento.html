3. Multi-tenancy — múltiples clientes simultáneos

La app soporta múltiples empresas operando simultáneamente con aislamiento total de datos Cada empresa cliente tiene su propio espacio de datos, su propia API Key, su propio mapeo de campos y su propia configuración de La Mundial. Un cliente nunca puede ver ni afectar los datos de otro.

Cómo funciona el aislamiento

Cada viaje en la base de datos tiene un tenant_id que apunta a la empresa propietaria. Todas las consultas filtran automáticamente por ese ID. Es imposible para una empresa acceder a viajes de otra.

Qué configura cada empresa de forma independiente

4. Sistema de cero errores en emisión de pólizas — 5 capas de protección

El problema crítico: una póliza sin emitir en el momento de un accidente es una catástrofe Si La Mundial de Seguros está temporalmente caída justo cuando inicia un viaje, el conductor quedaría sin cobertura RCV. El sistema fue diseñado para que esto jamás ocurra sin al menos 3 horas de reintentos automáticos y vigilancia continua.
Aclaración importante sobre los "errores" de las pruebas de estrés Los errores del 2.7%–3% que aparecen en las pruebas con 500+ conexiones simultáneas NO son pólizas perdidas. Son el script de prueba que desconectó su conexión después de 20 segundos (timeout del cliente de prueba). El servidor siguió procesando y los viajes quedaron guardados. En producción, Ridery esperaría o reintentaría automáticamente.

Las 5 capas de protección

1
Emisión sincrónica inmediata SIEMPRE ACTIVO
Al recibir el evento de inicio de viaje, el servidor llama a La Mundial en ese mismo instante. Si responde (caso normal, <1 segundo), la póliza queda ACTIVA de inmediato. El viaje siempre se guarda en BD antes de llamar a La Mundial, garantizando que nunca se pierde aunque La Mundial falle.
2
BullMQ — 10 reintentos automáticos hasta 3 horas SI CAPA 1 FALLA
Si La Mundial no responde, se encola automáticamente un job con 10 reintentos en backoff exponencial: 10s → 20s → 40s → 1.3min → 2.7min → 5.3min → 10.7min → 21min → 43min → 85min. Cubre cortes de La Mundial de hasta 3 horas sin intervención. Los jobs sobreviven reinicios del servidor gracias a Redis AOF.
3
PolizaGuardian — Escáner periódico cada 5 minutos RED DE SEGURIDAD
Un proceso cron (PolizaGuardianService) revisa la base de datos cada 5 minutos buscando viajes con estadoPoliza = ERROR, CRITICO, o EMITIENDO por más de 5 minutos. Re-encola automáticamente los que no se han intentado recientemente. Actúa aunque Redis o BullMQ hayan fallado completamente. Cubre hasta 50 rescates simultáneos por ciclo.
4
Redis AOF Durabilidad total INFRAESTRUCTURA
Redis configurado con appendonly yes + appendfsync always: cada job se escribe al disco físico antes de confirmar. Si el servidor se apaga abruptamente (corte de luz, crash del OS), ningún job pendiente se pierde. Al reiniciar, BullMQ retoma exactamente donde quedó. Además maxmemory-policy noeviction: Redis jamás descarta jobs para liberar memoria.
5
Panel de alertas para el operador MONITOREO HUMANO
El endpoint GET /api/admin/polizas-criticas retorna en tiempo real todos los viajes con póliza pendiente. Se puede conectar a Uptime Robot, Grafana o cualquier monitor externo para recibir alertas si total > 0. Muestra estado ERROR (retrying), CRITICO (reintentos agotados, guardian activo) y EMITIENDO atascado.

5. Escalado automático — clustering y crecimiento

Respuesta a: ¿Worker Threads o Clustering? Para un API REST I/O-bound (espera BD, espera La Mundial), la respuesta correcta es Cluster de procesos, no Worker Threads. Los Worker Threads sirven para trabajo CPU-intensivo (IA, imágenes). Nuestro servidor pasa el 95% esperando respuestas de red — cluster es la opción correcta y ya está implementada.

Cómo activar el escalado automático

Variable de entornoComportamientoUso
NODE_ENV=production1 worker por CPU automáticamente. 8 CPUs = 8 workers.Producción
CLUSTER_WORKERS=4Fuerza exactamente 4 workers en cualquier ambiente.Staging / pruebas
NODE_ENV=development1 proceso. Hot-reload y debugging funcionan normalmente.Desarrollo
Auto-heal incluido: si un worker muere, el servidor lo reinicia solo cluster.on('exit', () => cluster.fork()) — ante cualquier crash inesperado, el proceso principal lanza un nuevo worker automáticamente sin intervención.
